# 팀 프로젝트 기능 시연 보고서

## 1. 문서 목적

이 문서는 월계 재능나눔 서비스에 구현한 **역할 기반 팀 프로젝트 기능**을 발표·검수 환경에서 재현하기 위한 시연 보고서다.

기존 팀 프로젝트는 다음 문제가 있었다.

- 학생이 어떤 역할로 지원하는지 구분되지 않았다.
- 첫 번째 학생을 선발하면 프로젝트가 바로 시작됐다.
- 역할별 모집 정원을 서버에서 검사하지 않았다.
- 디자인·개발 등 역할이 달라도 같은 활동 질문을 사용했다.
- 팀원이 다른 팀원의 개인 답변과 활동 기록을 볼 수 있었다.
- 모든 팀원이 최종 결과물을 제출할 수 있었다.
- 프로젝트가 승인되면 실제 참여 여부와 관계없이 모든 팀원이 같은 검증을 받았다.
- 검증되지 않은 팀원도 개인 포트폴리오를 만들 수 있었다.

이번 구현은 팀 프로젝트를 다음 흐름으로 변경했다.

```text
역할별 팀 공고 등록
→ 학생별 역할 선택 지원
→ 역할별 지원자 선발
→ 모든 역할 충원
→ 팀장 지정 및 프로젝트 시작
→ 역할별 질문과 개인 활동 기록
→ 팀장의 최종 결과물 제출
→ 의뢰인의 팀원별 실제 참여 검증
→ 검증된 팀원끼리 상호평가(본인 제외)
→ 검증된 팀원의 개인 포트폴리오 생성
```

## 2. 구현 범위

### 2.1 역할별 모집

- 의뢰인은 팀 공고에 역할명, 카테고리, 모집 인원을 설정한다.
- 예: `디자이너 / 디자인 / 1명`, `프론트엔드 개발자 / 웹·앱 / 1명`.
- 학생은 지원할 역할을 반드시 선택한다.
- 지원 역할이 공고에 없거나 해당 역할의 정원이 찬 경우 서버에서 선발을 차단한다.

### 2.2 팀 구성과 시작

- 첫 번째 팀원을 선발해도 프로젝트 상태는 `RECRUITING`으로 유지된다.
- 모든 역할의 모집 인원이 충족되어야 프로젝트를 시작할 수 있다.
- 의뢰인이 선발된 팀원 중 팀장을 지정하고 **팀 확정하고 시작**을 눌러야 `IN_PROGRESS`로 전환된다.

### 2.3 팀원별 질문과 기록 분리

- 팀원은 자신이 지원한 역할의 분야에 맞는 질문을 받는다.
- 디자인 역할은 `DESIGN`, 개발 역할은 `DEVELOPMENT` 질문 스냅샷을 사용한다.
- 답변, 중간 기록, 증빙, 성과는 작성자 ID로 분리된다.
- 진행 중에는 학생이 다른 팀원의 개인 기록을 조회할 수 없다.
- 의뢰인은 프로젝트 관리와 검증을 위해 모든 팀원의 기록을 팀원별로 확인할 수 있다.
- DB에 직접 요청하더라도 자신의 역할에 포함되지 않은 질문은 저장할 수 없다.

### 2.4 팀장 전용 최종 제출

- 일반 팀원은 개인 활동 기록과 증빙을 남길 수 있다.
- 최종 결과물 버전 제출은 지정된 팀장만 할 수 있다.
- 화면뿐 아니라 DB 트리거에서도 일반 팀원의 제출을 차단한다.

### 2.5 팀원별 검증과 포트폴리오

- 의뢰인은 최종 결과물을 검토하면서 실제 참여한 팀원을 개별 선택한다.
- 참여가 확인된 팀원만 다음 결과를 받는다.

  - 검증 프로젝트 이력
  - 기여 점수와 배지
  - 자신의 역할 분야 배지
  - 개인 활동 기록을 기반으로 한 포트폴리오 생성 권한

- 참여 확인을 받지 못한 팀원은 해당 프로젝트로 포트폴리오를 만들 수 없다.
- 각 팀원의 포트폴리오는 본인의 답변, 중간 기록, 증빙, 성과를 중심으로 생성된다.
- 팀장이 제출한 승인 결과물처럼 프로젝트 공통 자료는 팀 포트폴리오 근거로 포함될 수 있다.

### 2.6 팀원 상호평가

- 프로젝트 완료 후 실제 참여가 확인된 팀원끼리 평가할 수 있다.
- 본인은 평가 대상에서 제외된다.
- 소통·협력·책임감을 각각 1~5점으로 평가한다.
- 같은 프로젝트에서 받은 팀원 평가의 평균을 협업 온도에 반영한다.

## 3. 시연 시나리오

### 3.1 시연 데이터

| 구분 | 이름 | 역할 |
|---|---|---|
| 의뢰인 | 월계커피 | 팀 공고 등록·선발·검증 |
| 학생 A | 김하늘 | 디자이너, 팀장 |
| 학생 B | 박도윤 | 프론트엔드 개발자, 일반 팀원 |

팀 공고 예시:

| 항목 | 내용 |
|---|---|
| 제목 | 월계커피 모바일 주문 페이지 개선 |
| 문제 | 메뉴 정보가 흩어져 있고 모바일 주문 동선이 복잡하다. |
| 역할 1 | 디자이너 · 디자인 · 1명 |
| 역할 2 | 프론트엔드 개발자 · 웹/앱 · 1명 |
| 기대 결과물 | 모바일 화면 시안, 주문 페이지, 테스트 결과 |
| 완료 기준 | 주요 메뉴 조회부터 주문 요청까지 모바일에서 동작 |

### 3.2 사전 준비

1. 앱을 실행한다.

   ```bash
   npm run dev
   ```

2. 브라우저에서 [http://localhost:3000](http://localhost:3000)에 접속한다.
3. 실제 Supabase 모드에서는 의뢰인 계정 1개와 학생 계정 2개를 준비한다.
4. 여러 계정을 동시에 사용할 경우 일반 창, 시크릿 창, 다른 브라우저 프로필을 각각 사용한다.

## 4. 단계별 시연 절차

### 단계 1. 역할별 팀 공고 등록

1. 의뢰인 계정으로 로그인한다.
2. **공고 등록**으로 이동한다.
3. `여러 명이 필요한 팀 프로젝트예요`를 선택한다.
4. 다음 역할을 추가한다.

   - 역할 이름: `디자이너`, 카테고리: `디자인`, 인원: `1명`
   - 역할 이름: `프론트엔드 개발자`, 카테고리: `웹/앱`, 인원: `1명`

5. 공고를 등록한다.

**확인할 결과**

- 공고 상세에 두 역할과 각각의 모집 현황 `0/1`이 표시된다.
- 역할명이 단순 카테고리와 구분되어 표시된다.

### 단계 2. 학생별 역할 선택 지원

1. 학생 A로 로그인하고 `디자이너` 역할을 선택해 지원한다.
2. 학생 B로 로그인하고 `프론트엔드 개발자` 역할을 선택해 지원한다.

**확인할 결과**

- 역할을 선택하지 않으면 지원할 수 없다.
- 의뢰인 화면의 지원자 목록에 각 학생의 지원 역할이 표시된다.
- 이미 정원이 찬 역할은 추가 선발할 수 없다.

### 단계 3. 역할별 선발과 팀 구성

1. 의뢰인 계정에서 학생 A만 먼저 선발한다.
2. 프로젝트 화면으로 이동한다.
3. 아직 개발자 역할이 비어 있는 상태에서 팀 시작을 시도한다.

**확인할 결과**

- 프로젝트 상태가 `RECRUITING`으로 유지된다.
- `프론트엔드 개발자` 인원이 부족하다는 안내가 표시된다.
- 첫 번째 팀원을 선발했는데 프로젝트가 바로 시작되는 기존 문제가 재발하지 않는다.

4. 학생 B도 선발한다.
5. 학생 A를 팀장으로 지정한다.
6. **팀 확정하고 시작**을 누른다.

**확인할 결과**

- 프로젝트 상태가 `IN_PROGRESS`로 바뀐다.
- 학생 A 옆에 팀장 표시가 나타난다.
- 공고 상태가 진행 중으로 변경되어 추가 지원을 받지 않는다.

### 단계 4. 역할별 질문 확인

1. 학생 A로 프로젝트의 **활동 기록**에 들어간다.
2. 디자인 문제, 시안, 디자인 결정과 관련된 질문을 확인하고 답한다.
3. 학생 B로 같은 프로젝트의 **활동 기록**에 들어간다.
4. 구현 방법, 기술 선택, 테스트와 관련된 개발 질문을 확인하고 답한다.

**확인할 결과**

- 두 학생에게 서로 다른 역할별 질문이 표시된다.
- 학생 B가 디자인 질문 ID를 임의로 저장하려 하면 DB가 `INVALID_QUESTION`으로 거부한다.
- 질문 목록은 팀원 선정 시점 스냅샷으로 고정된다.

### 단계 5. 개인 기록과 증빙 분리

1. 학생 A가 디자인 시안 결정 과정을 중간 기록으로 남기고 시안 이미지를 올린다.
2. 학생 B가 API 연결과 모바일 테스트 과정을 기록하고 테스트 자료를 올린다.
3. 학생 A 화면에서 학생 B의 개인 기록이 보이는지 확인한다.
4. 의뢰인 화면에서 두 팀원의 기록을 확인한다.

**확인할 결과**

- 학생에게는 `내 중간 기록`, `내 증빙`만 표시된다.
- 학생 A는 진행 중인 학생 B의 개인 기록을 DB 조회로도 볼 수 없다.
- 의뢰인에게는 작성자 이름과 함께 팀원별 기록이 표시된다.

### 단계 6. 팀장 전용 최종 제출

1. 일반 팀원인 학생 B가 결과물 제출 화면에 접근한다.
2. 학생 A가 팀의 결과물 증빙을 선택하고 최종 버전을 제출한다.

**확인할 결과**

- 학생 B에게 `팀장만 팀의 최종 결과물을 제출할 수 있어요`가 표시된다.
- 직접 API를 호출해도 DB가 `LEADER_ONLY`로 차단한다.
- 학생 A의 제출만 `REVIEW_PENDING`으로 전환된다.

### 단계 7. 팀원별 실제 참여 검증

1. 의뢰인 계정으로 제출 버전을 검토한다.
2. 결과물과 완료 기준을 확인한다.
3. `실제 참여한 팀원을 확인해 주세요`에서 검증할 팀원을 선택한다.
4. 검증 항목과 평가를 입력하고 승인한다.

시연을 명확하게 하기 위해 학생 A만 체크하고 학생 B는 체크하지 않는다.

**확인할 결과**

- 프로젝트는 `COMPLETED`가 된다.
- 학생 A의 `member_verifications.verified`는 `true`가 된다.
- 학생 B의 값은 `false`가 된다.
- 학생 A에게만 검증 점수, 배지, 활동 카드가 생성된다.

### 단계 8. 팀원별 포트폴리오 생성

1. 학생 A로 완료된 프로젝트에 들어가 **포트폴리오 만들기**를 누른다.
2. 생성된 포트폴리오에서 디자인 역할, 학생 A의 답변·기록·증빙이 사용됐는지 확인한다.
3. 학생 B로 같은 프로젝트에 들어간다.

**확인할 결과**

- 학생 A는 개인 포트폴리오를 생성할 수 있다.
- 학생 A의 포트폴리오는 `DESIGN` 분야 템플릿과 디자인 역할 배지를 사용한다.
- 학생 B에게는 실제 참여 확인이 필요하다는 안내가 표시된다.
- 학생 B가 직접 생성 요청을 보내도 DB와 Edge Function이 `NOT_VERIFIED`로 차단한다.

### 단계 9. 팀원 상호평가와 협업 온도

1. 별도 시연 프로젝트에서는 학생 A와 학생 B의 실제 참여를 모두 검증한다.
2. 학생 A로 완료된 프로젝트에 들어가 **팀원 상호평가**를 누른다.
3. 학생 B의 소통·협력·책임감을 각각 1~5점으로 평가하고 저장한다.
4. 본인이 평가 대상에 나타나지 않는지 확인한다.
5. 학생 B의 `나` 화면에서 협업 온도를 확인한다.

**확인할 결과**

- 실제 참여가 검증된 학생만 상호평가 화면에 접근한다.
- 본인은 평가 대상에서 제외된다.
- 평가받은 팀원의 프로젝트별 평균 점수가 협업 온도에 반영된다.
- 의뢰인은 프로젝트 검증과 기존 만족도 평가를 계속 담당한다.

- 팀장 지정과 명시적 시작
- 역할별 질문 스냅샷 저장
- 다른 역할 질문 저장 차단
- 진행 중 팀원 간 개인 기록 조회 차단
- 일반 팀원 최종 제출 차단
- 팀장 최종 제출 허용
- 팀원별 검증 결과 분리
- 미검증 팀원의 점수·활동 카드 생성 방지
- 미검증 팀원의 포트폴리오 생성 차단
- 검증된 팀원의 개인 포트폴리오 생성 허용

- 본인 상호평가 차단

## 8. 시연 성공 기준

다음 항목이 모두 확인되면 팀 프로젝트 시연을 성공으로 본다.

- [ ] 학생이 역할을 선택해 지원한다.
- [ ] 의뢰인이 역할별로 학생을 선발한다.
- [ ] 모든 역할이 채워지기 전에는 시작할 수 없다.
- [ ] 팀장을 지정해야 프로젝트가 시작된다.
- [ ] 역할마다 다른 활동 질문이 표시된다.
- [ ] 학생은 자신의 기록만 확인한다.
- [ ] 의뢰인은 팀원별 기록을 확인한다.
- [ ] 팀장만 최종 결과물을 제출한다.
- [ ] 의뢰인이 실제 참여 팀원을 개별 검증한다.
- [ ] 검증된 팀원만 개인 포트폴리오를 생성한다.
- [ ] 검증된 팀원끼리만 상호평가하며 본인은 평가 대상에서 제외된다.
- [ ] 팀원 평가 평균이 협업 온도에 반영된다.
